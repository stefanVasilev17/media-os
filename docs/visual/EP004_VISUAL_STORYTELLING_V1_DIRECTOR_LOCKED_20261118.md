## Visual story spine

We tell a three-stage mystery inside one persistent map: **human consequence → discover the hidden conditions → watch recovery become a new failure.** At the end we replay the complete architecture from the user's perspective and turn the failure into precise engineering lessons.

**Mental map:** Client / Outlook and Teams sources (left) → traffic routing (middle-left) → `Primary Gateway` and `Alternative Gateway` paths (middle) → conceptual Gateway Fleet, Capacity and Connection Handling (focus planes) → Exchange Online and Teams destinations (right). All nodes exist in one logical world, with spatial depth rather than stacked framed panels. The camera makes local parts large. It returns from those parts along the same actual visual corridor. Before a relevant part is introduced it is hidden or dim; after explanation it remains QUIET, never deleted and reintroduced as though brand-new.

**Visual language:** dark navy `#010711`/`#020811`; Outlook cyan, Teams violet; context dim blue-gray. State amber waiting, red failed, green completed. Identity colors do not override state colors. Requests move on exact Bezier/orthogonal rendered path coordinates; route changes follow explicit connectors, no teleporting. Distinguish traffic request from response by shape and direction. A capacity meter measures remaining available fleet capacity; node health means responsiveness; internal contention pressure means ability to establish connections. These are different values. Don't put them on one fake 100% meter.

**One critical visual distinction:** Show a percentage bar when saying **~14% unavailable**, but do not display 'one out of seven physical servers failed' as if that were evidence. Show another percentage bar when saying **>80% of affected gateway servers unresponsive**, not an invented concrete server count. When visualizing lock contention and health checks, place a small unobtrusive `Conceptual model` label near the local focus—not a repeated giant disclaimer or floating teaching slide.

**Main narrative object:** A single Outlook mailbox attempt appears at start and returns at end. A violet Teams stream enters the primary corridor at the documented earlier failover. Both continuously follow exact connections. The gateway fleet becomes the central protagonist: healthy, pressured, fragmenting, restarting, recovering, then providing a stable route.

**Camera:** `CLOSE` for human or local mechanism; `MEDIUM` for a gateway and immediate dependencies; `WIDE` for flow and comparisons; `FULL MAP` only SHOT14 as a well-earned synthesis and SHOT15 brief closing aftermath. Semantic moves only. 2-second silent intro/outro if voice edit supports, never arbitrary static pads. Preserve previous decoded SHOT last-frame continuity at next SHOT local frame 0, including current camera, active route and packet positions.

**Text overlay policy:** Architecture labels, short factual percentage/time indicators, and brief glossary definitions when the VO introduces the term. No info panels and no paragraphs. `FAILOVER` and `LOCK CONTENTION` may have one legible glossary reveal each. For more complex points, use slow motion and repeated examples, not extra text. Any visual written sentence is a complete readable English sentence; short state labels may be fragments. Text clipping is a hard failure. The same world and real component primitives carry all episodes. This plan specifies desired components, not confirmation that those primitives already exist in the current repository.

## SHOT 01 — AN ORDINARY WORKDAY STOPS (00:00–01:05)
**Story purpose:** Enter via a human action. Start a question we will answer only after the cascade and recovery. **First frame:** a familiar small Outlook mailbox view inside the recurring client anchor, not a fake widescreen browser mockup. **Exit frame:** blocked request corridor toward distant gateways, ready to open into the failover demonstration in SHOT02.

**P01 — “On November twelfth ... a cloud service had simply gone down.”** Show one ordinary moment: unread mail rows, cursor selects inbox, a deliberate mailbox request starts. The camera does not jump to a dramatic red screen. Track the cyan request along a real curved connector from client toward the partly obscured gateway boundary. As the packet reaches the boundary, movement slows and ends in an amber waiting state, then marks the route unavailable. Under the narrator's delayed-email phrase, one small message token stays waiting without claiming that every Microsoft 365 application was down. Other product symbols remain QUIET, with no red failure state. The viewer understands exactly one observable consequence: mailbox access failed.

**P02 — “But behind that familiar error ... unresponsive again.”** While the client remains at the left edge, pull back slightly to reveal a small cluster of potential gateway endpoints, still mostly dim. A cyan path that seems to offer a second route begins to illuminate; it does not magically transport the earlier packet. Briefly show a conceptual endpoint switching red → amber restart → green response and then amber/red again as a subtle foreshadow, without giving the mechanism away. Use one restrained motion loop, not three concurrent flashing alerts. The viewer should now wonder why an apparently recovered machine fails again.

**P03 — “The central question ... part of the failure?”** Hold a composition that places the blocked client on the left, a routing junction in focus, and the still-unrevealed alternate gateway corridor on the right. One intact standby path is visible but dim. A short light travels along the router's choice path, then halts before the unknown fleet. No giant question headline. A natural audio pause gives the question weight; the camera starts its gentle approach toward the routing junction, continuing into SHOT02.

**Transition 01→02:** No hard reset. Transform the active human request into a clean conceptual routing example at the same world location. The real-world outage is temporarily paused while we teach the necessary concept.

## SHOT 02 — THE PROMISE OF FAILOVER (01:05–02:15)
**Story purpose:** Teach the normal, correct behavior of a failover system before exposing its hidden assumption. This is a labeled **illustrative routing demonstration**, not a claim about Microsoft’s exact endpoint layout.

**P01 — “Imagine a service with several servers ... failover.”** The camera arrives at an existing Traffic Router. Reveal three stylized gateway destination nodes along physically drawn routes, arranged to be readable rather than numerous. Send three separate cyan requests from a client: each follows a visible connector, reaches a green responding endpoint, and a distinct smaller response returns via its reverse route. Then one destination turns unavailable. For the next *new* request, the router selects a different drawn branch; an earlier in-flight packet is not teleported. Show the old path dim while the new path activates. When VO says `failover`, optionally show a concise definition for ≥5.5 seconds: `FAILOVER — Moving work to another available path`. The picture alone should explain the term even without reading the definition.

**P02 — “This is not a bad idea ... disappoint its users.”** Highlight the benefit, not the failure. Run a successful request/response on the alternate endpoint; both source client and returned response briefly turn RESOLVED. Represent hardware, software, and network causes as three quick visual *variations* of one failure state on the same route (node offline, process unavailable, connector blocked), sequentially, not three new diagrams. Keep the other destinations accessible. End on a healthy recovered application response: the core promise of redundancy has now been demonstrated.

**P03 — “But failover quietly makes an assumption ... close to its limit.”** Shift focus from a green status indicator to the endpoint's remaining working capacity. Above/adjacent to each server, reveal a thin load/available-headroom indicator, never a large card. Demonstrate the second endpoint receiving the redirected traffic and its headroom shrinking, even while the node continues glowing healthy. Next, show a quiet identical vulnerability marker inside *both* destinations, but do not call it the Microsoft bug yet. A green route remains visible while the endpoint's spare headroom becomes amber. The viewer must see: `reachable` and `safe to receive more load` are not the same condition.

**P04 — “And that is where this story begins.”** Stop the demonstration. Keep the concept visually remembered as quiet nodes, then track the camera down the already-existing connection spine to the pair of large gateway corridors. The router and one recent redirect stay in the background so the scene feels like entering the true story through the mechanism just learned.

**Transition 02→03:** A continuous camera move from the generic endpoint example toward the two incident gateway systems. Remove the demonstration's example-only labels as focus changes, not by wiping the world.

## SHOT 04 — THE BUG THAT WAITED SINCE JULY (03:35–05:10)
**Story purpose:** Explain the invisible defect and the surprising hardware-testing mismatch in understandable visual terms.

**P01 — “Back in July ... gateway environment described in Microsoft's report.”** On the gateway's internal focus plane, introduce a short code-version indicator `July gateway update` and animate an understated deploy marker moving along a small sequence of conceptual fleet nodes, each updating quietly. Do not show a Windows desktop, a global OS update, or a fabricated change log. A tiny amber vulnerability marker becomes latent behind the `Connection Handling` label, but all requests still succeed. Travel on a compact timeline line from July to November with an uneventful interval; the absence of visible failure is the storytelling point.

**P02 — “Under certain load conditions ... unresponsive.”** Push into an exploded connection-handling mini-world *attached to* the gateway, not a stack of smaller boxes. A single shared resource appears as a constrained access point. Work items enter via a thin real path. One crosses the resource and exits successfully; the next two must pause before the resource. On the narrator's term, a small glossary `LOCK CONTENTION — Multiple operations wait for one shared resource` appears, then leaves after adequate reading time. Additional arrivals accumulate as abstract pressure bands along the entry path, not as an asserted literal internal Microsoft queue. Thread activity visibly slows; adjacent illustrative CPU and memory pressure indicators rise with no precise measurements. The node transitions healthy → amber → unresponsive. All motion is about blocked progress rather than random jitter.

**P03 — “Now comes an unusual detail ... more CPU cores.”** Pull sideways within the same focused gateway world into a comparison of two *visual conditions*, `Load Test` versus `Production`. Do not compare invented clock speeds or core counts. The smaller test condition has fewer parallel work lanes and the contented shared resource remains manageable under its test traffic. The more parallel production condition has visibly more simultaneous arrivals and a different mix of tokens; the same shared resource becomes a bottleneck. Highlight `More cores` and `Different traffic mix` only when narrator introduces them, one at a time. Position the model as illustrative rather than proof of exact Microsoft hardware behavior.

**P04 — “More powerful hardware did not automatically mean a safer test.”** Hold a clear two-state contrast: on one side, a lower-parallelism simulation passes; on the other, higher concurrency reveals a waiting cluster. On the emphasized line, gently dim the test example, keep the production failure focal, and then collapse both back to the actual gateway location. The final visible object is a latent defect marker anchored in every conceptual member of the same gateway fleet, not floating in disconnected empty space.

**Transition 04→05:** Camera exits the selected gateway back onto the fleet plane. The defect marker remains dim as knowledge we carry into the next condition.

## SHOT 05 — FOURTEEN PERCENT OF CAPACITY WAS ALREADY MISSING (05:10–06:35)
**Story purpose:** Teach the independent capacity reduction before showing how it interacts with the Teams traffic shift and the software defect.

**P01 — “The hidden software defect ... under its earlier conditions.”** Reveal a clean percentage capacity track next to the primary gateway fleet labeled `Available Gateway Capacity`. Present 100% conceptual baseline as a single bar, then dim exactly about 14% of that bar and label `~14% unavailable`. This is **capacity share, not a claim about a count of physical machines**. Keep most fleet nodes green, and maintain successful Outlook response motion. Show no red global outage. The viewer learns that losing capacity was a condition the system initially tolerated.

**P02 — “Think of capacity as breathing room ... platform is available.”** Inside the same scene, represent free headroom as an unfilled portion of a thin capacity/load band. As normal packets pass, show a margin between offered load and available work. Remove the 14% segment: the margin shrinks, but requests continue to complete and nodes keep their healthy state. On `dashboard can still show available`, show a restrained `SERVING` state and contrast it with the visibly smaller spare margin. No large dashboard UI, and no suggestion that actual Microsoft monitoring looked exactly like this.

**P03 — “Then change the work arriving ... bug would appear.”** Restore the previously learned violet Teams path into view; animate Teams requests arriving into the same primary gateway on an explicitly drawn connector. Cyan continues at the previous rate while violet joins. The load band advances toward available capacity, and the July defect marker becomes amber on one focused gateway. For `peak U.S. traffic`, use one compact geographic/time-context label rather than an invented real Microsoft regional traffic chart. Time enough for the viewer to compare the available capacity against the newly combined offered work.

**P04 — “Neither the missing capacity nor the earlier traffic shift ... combination ...”** This paragraph is a crucial **visual Aha**. Without leaving the map, briefly show three states sequentially on the *same* gateway: `Reduced capacity alone` still serving; `Changed traffic mix alone` still serving in illustrative comparison; `Together + latent bug` triggers amber contention. If we use captions, each is a tiny anchored condition label and not a multi-card slide. Do not imply either condition was tested in real isolated Microsoft trials. The final state fixes all three known conditions in the viewer's mind: latent bug, capacity reduction, Teams routing shift.

**Transition 05→06:** Stay in the primary gateway fleet and push through the one endpoint just turning amber. Next we follow work that cannot complete, rather than introducing another place.

## SHOT 06 — WHEN THE ROUTE CHANGES, SO DOES THE RISK (06:35–07:55)
**Story purpose:** Make the connection between incoming traffic, constrained progress, and gateway failure physically visible.

**P01 — “At first, the extra traffic ... hidden boundary is crossed.”** Show ongoing requests being answered despite rising pressure. A delicate work-concurrency line grows toward an unlabeled caution band while completed response packets become less frequent. Crucially, this is not a magic CPU overload triggered by an arbitrary number. The animation demonstrates qualitative load sensitivity, not an asserted numerical threshold. The camera remains close enough to count individual accepted work items, then begins to widen only when the effect reaches server availability.

**P02 — “Imagine connections arriving slightly faster ... stop answering.”** Stage a clear progression across the internal path: incoming requests arrive → a few complete → several wait at shared access → the span of waiting work grows → CPU/memory pressure rises → fewer completions exit → the endpoint stops responding. Convey the waiting pressure as a longer accumulation on the existing inlet corridor, *not an invented literal FIFO queue implementation*. The single gateway's ACTIVE outline becomes WAITING amber, then FAILED red. Every cyan/violet request stops at a valid physical route endpoint; no particle passes through a failed node and reappears on the far side.

**P03 — “This is why a traffic graph alone can mislead ... surviving endpoint.”** Pull back to contrast a steady approximate *total incoming demand* indicator on the router against a smaller number of available gateway destinations. Visually distribute the same incoming request rate across three conceptual nodes, then across two: each surviving node's received request spacing becomes tighter, while the total ingress stream looks nearly unchanged. This is a general explanatory model and uses no actual Microsoft node count. Show that total platform demand and per-server load are separate dimensions.

**P04 — “The danger was not simply ... when it arrived.”** Trace one cyan request from the constant ingress stream to the newly crowded endpoint and stop with the latent bug marker highlighted. On `where traffic went`, illuminate the path choice; on `what it triggered`, illuminate the contention point in the destination. Pull back far enough to include the route and endpoint in the same field of view. The last frame has one failed gateway and two surviving endpoints, setting up the cascade without a scene reset.

**Transition 06→07:** Keep the same router, same failed endpoint and same stream of requests. SHOT07 begins by moving *new* traffic onto drawn alternate connectors.

## SHOT 07 — THE CASCADE (07:55–09:35) — REEL 01
**Story purpose:** Deliver the central surprise: automatic rerouting repeatedly transfers extra work onto destinations with the same weakness. **Reel boundary:** the separate voiced paragraph beginning `A backup server is not automatically a rescue.` Its first visual frame must already explain the initial condition without relying on shots 01–06.

**P01 — “When a gateway stopped responding ... through the fleet.”** At the inherited shot start, node A is red, B and C remain responsive. The traffic router does not touch existing in-flight packets. It diverts subsequent requests over an explicit highlighted branch toward B; the valid path from A to its destination goes QUIET because A cannot serve. Node B now receives its normal flow plus the new flow, so its load indicator moves closer to the edge. Repeat one step: B becomes amber and then fails, while new traffic turns toward C. Keep the fleet spatially fixed so pressure is shown as a consequence of redirection, not as mysterious movement of boxes.

**P02 — “Microsoft's preliminary report ... more than eighty percent ... follow one request.”** Widen to a fleet-level percent meter `>80% of affected gateway servers unresponsive`. Do **not** pretend that our three illustrated gateways correspond to the actual incident's server count. Allow the three-node teaching diagram to scale into a broader field of dim/unresponsive gateway silhouettes while the percent meter communicates the verified approximate fleet condition. During `less than two hours`, a small clock bracket marks this period, not a false second-by-second replay. Then zoom onto one new request at the router for the short-form extraction: `follow one request` becomes a concrete visual handoff.

**P03 — Reel 01: “A backup server is not automatically a rescue ... spread the failure.”** Build this as a self-contained 40–50 second miniature in a center-safe area. **Beat A, Hook:** center router, one client, two alternative gateway destinations; one destination is already unresponsive and the alternate route is visibly ready. **Beat B, Rescue:** a *new* cyan request follows the router → B connector and completes once; B still green, so the viewer trusts the reroute. **Beat C, Pressure:** multiple new arrivals now take B's route while B's spare headroom shrinks, then internal vulnerability activates amber. **Beat D, Repeat:** B stops responding, the router selects C via an explicitly drawn path, and C's workload becomes dangerous. **Beat E, Payoff:** camera widens slightly enough to see one router and several failed endpoints while the router's routing-decision indicator remains green. On `every local rescue decision`, green local routing contrasts with red whole-system availability. The final spoken line has a stable, understandable frame, not a flurry of effects. In vertical crop retain client → router → B/C, never require important left/right extremes.

**Transition 07→08:** Stop following one request. Pull back to see the gateway fleet as capacity partitions within regions; the red outage state persists in all relevant previously explained nodes.

On `bulkhead`, briefly brighten the separating boundary. No ship illustration is needed: the audience understands the analogy through containment. The key visual sentence is one red zone and two unaffected zones.

**P02 — “Microsoft said its gateway infrastructure ... much more widely.”** Return from the safe design example to the incident state on the same world. A second independent issue is represented by the *loss of effective containment*, not a fabricated line showing exactly how Microsoft routed packets between regions. Gradually light red affected-status bands in additional regions while a shared incident impact marker spans them. ## SHOT 09 — WHY HEALTHY IS NOT THE SAME AS SAFE (11:00–12:25)
**Story purpose:** Explain liveness/readiness distinction in a way that prepares the viewer for failed recovery. The diagnostic split is a **general engineering lens**, not an assertion that Microsoft's actual probes worked this exact way.

**P01 — “Now imagine watching one ... immediately send ... traffic?”** In close view, one gateway is FAILED red. Its restart sequence begins quietly: process marker off → starting amber → online green. A single narrow `Health check` request travels along a real probe path and receives a response, making a green `RESPONDING` light appear. Meanwhile, outside the gateway, many client requests remain visibly ready to arrive. At the spoken question, let the traffic router's outgoing connector glow slightly but do not release the full stream yet. Give the audience a second to notice the difference between a tiny check and a large production load.

**P02 — “That question separates two ideas ... different question.”** Divide the camera's attention between the same node's simple probe route and its genuine client-request connector; do not create two replacement scenes. Label short, anchored states `ALIVE` and `READY FOR LOAD` as two separate dimensions. A single green liveness result cannot automatically illuminate readiness. Demonstrate one small successful probe, then a modest batch of client requests increasing pressure under the still-unsolved defect. The node may be alive while its load readiness remains amber. Make this a visual comparison between *test size* and *real offered work*, not merely between green and red.

**P03 — “Microsoft's incident updates ... contention could return.”** Move the simple health-check indicator into QUIET, because it is contextual. The narrator references Microsoft's work on health-check behavior; represent that investigation with a restrained probe-route adjustment, not a made-up exact operational algorithm. Reintroduce the preexisting contention marker in the gateway and show increasing load could reactivate it. Preserve the accurate causal conclusion: changing a check cannot by itself fix the load-sensitive underlying issue.

**P04 — “A recovery system must therefore ask ... when we reconnect users?”** Show two short questions sequentially near the object, not large cards: first `Running?` with a green response, then `Can it handle returning traffic?` while real packets are admitted gradually on the existing path. If the second question does not have proof, show an amber `NOT YET PROVEN` state. The visualization explicitly separates observable health from capacity-under-load. Give enough dwell for the viewer to read the second phrase, or omit the written question and let the voice carry it.

**P05 — “A green endpoint is helpful ... service.”** Pull to medium, keep one restarted node green at its basic probe indicator, but hold its capacity headroom amber. No red state is needed yet. Create the moment of intellectual tension: the node looks online, the router path exists, users are still waiting. Then start opening the traffic route, carrying the audience directly into the restart-and-overload mechanism of SHOT10.

**Transition 09→10:** No reset; continue the node's restart from the final state and release the real returning traffic along the same connector.

## SHOT 10 — RESTARTING THE SERVERS MADE RECOVERY HARDER (12:25–13:50) — REEL 02
**Story purpose:** Make recovery the second dramatic failure loop. It must be visually distinguishable from initial cascade: a machine comes back, but returning demand reproduces the fault.

**P01 — “The hardest part of an outage ... fleet unresponsive at once.”** Stay on the same restarted gateway. A restart status travels amber → green. Instead of materializing a literal internal waiting queue, show **pending external demand** as subdued client request activity concentrated on the entrance corridor. When normal routing resumes, those real requests move onto the gateway connector. The demand indicator climbs faster than the gateway demonstrates sustained completion; the internal contention warning reappears and the gateway becomes unresponsive. Pull back just enough to show many similarly affected endpoints. Add one small `Fleet-scale recovery` label only if needed to explain why automated restart could not trivially solve the event.

**P02 — Reel 02: “Restarting a server is not the same as recovering a service ... keep it serving real users.”** Present a self-contained mini-sequence within the same gateway: **Hook:** one gateway red, people waiting outside. **Restart:** a compact status progress moves to green, one health probe succeeds. **Return traffic:** router opens a visible inlet, waiting client work begins moving toward the gateway. **Relapse:** request completions slow, the same contention point becomes amber, the gateway goes red again. **Contrast:** briefly rewind just this illustrative mechanism to show what *controlled admission* would look like as a future-safe design: fewer requests admitted, some held at the inlet, sufficient completion capacity demonstrated. This last alternative must be visibly labeled `Design principle`, not claimed as a precise Microsoft action during this paragraph. On the final line focus the actual response path reaching the client and remaining stable, as a definition of *service recovery* rather than mere process startup. Ensure the first vertical frame has the initial red node and waiting clients in the center; no outside narration context is required.

**Transition 10→11:** Leave the current overload frame stable. A thin temporal spine emerges along the already-seen gateway world, inviting the viewer to review how the states evolved over the incident. Do not replace the world with a generic text timeline slide.

## SHOT 11 — THE INCIDENT CLOCK (13:50–15:15)

**P02 — “Recovery teams tried several methods ... after traffic arrived.”** Continue the axis through the evening, but reduce the labels: `Traffic redistribution`, `Server restarts`, `Investigate health checks`, and later `Recovered nodes fail again`. The exact interventions are represented by previously taught objects: routing path brightness, server state sequence, probe route, repeat overload. ## SHOT 12 — HOW RECOVERY BECAME POSSIBLE (15:15–16:40)
**Story purpose:** Show recovery as the combination of a software fix and safe traffic reintroduction, not a magical single green switch.

**P01 — “A turning point came ... not immediately overwhelmed.”** At the existing `Connection Handling` focus, show the amber defective code-path marker replaced by a neutral `Known-good code path` marker. Animate a small update propagating *in ordered groups* across conceptual gateway endpoints, each starting amber, restarting, then becoming available. While this happens, the ingress corridor does not instantly open to full traffic: the route controller meters a narrower stream, and available gateway capacity gradually increases. Keep the update, rollout, traffic controls and capacity restoration distinguishable: one action repairs behavior, another governs demand. This is not a screenshot of Microsoft deploy tooling.

**P02 — “This matters because recovery had two jobs ... triggering it.”** Revisit the already familiar gateway at MEDIUM framing and stage a two-step comparison over the SAME node.
