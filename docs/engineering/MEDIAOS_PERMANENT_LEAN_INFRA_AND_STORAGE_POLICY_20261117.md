# MediaOS — P0 PERMANENT DIRECTOR LOCK: Lean Railway, Bounded Media Storage and Cost-Safe Production

**Policy ID:** `MEDIAOS-OPS-P0-20261117`  
**Director decision:** 2026-11-17 — permanent, episode-agnostic; applies to every agent, PR, deployment, SHOT, revision, QA operation, and future episode.  
**Priority:** P0 operational and financial safety requirement. It complements, does not replace, the Director-LOCKED roadmap, creative constraints, or verified master retention rules.  
**Source of truth:** this document; `AGENTS.md` mandates reading and applying it.  
**Status:** **DIRECTOR-LOCKED POLICY NOW**; some automatic checks below are **NOT YET IMPLEMENTED** and must be built and demonstrated, never claimed to exist merely because this Markdown was committed.

## Why this rule exists: hard-earned production evidence

On 2026-11-17, MediaOS had accumulated **50 Railway services** during development. Two redundant canary/second-Postgres services and **45 one-time SHOT/render/QA services** were retired, leaving **three** essential services. Main PostgreSQL formerly occupied **4.113 GB of a 5 GB volume**, mostly physical TOAST allocation left behind by deleted MP4 binaries; an off-volume checked backup followed by controlled `VACUUM FULL` reclaimed **3.031 GB**, leaving **1.082 GB used**. Primary Postgres memory had also climbed to ~3.95 GB dominated by file cache and was safely limited to 1.5 GB after investigation. This cannot become a repeating production procedure. Verified incident reports: `MEDIAOS_RAILWAY_ONESHOT_CLEANUP_COMPLETE_20261117.md`, `MEDIAOS_RAILWAY_COST_REDUCTION_20261117.md`, and `MEDIAOS_POSTGRES_DISK_RECLAIM_COMPLETE_20261117.md`.

## P0.1 — Infrastructure is shared; NO service per SHOT

1. The normal production service inventory is **exactly three long-running Railway services**: `media-os-backend`, `media-os-render-worker`, and `Postgres`. Keep the existing recovery object-storage bucket and protected Postgres volumes. A SHOT, scene, episode, take, revision, QA step, render, preview, video assembly or database diagnostic is **a job in the existing services, not a new Railway service**.
2. **PROHIBITED:** creating `epNNN-shotNN-*`, `*-once`, standalone canary, standalone voice/test/QA worker, new container/service/deployment target, per-SHOT database, per-episode volume, sidecar or cron-based worker merely to do normal production. Reuse the existing codebase and shared service; create no new paid AI provider or background agent process without the matching explicit Director gate.
3. Plan multi-SHOT work through a **single bounded job queue** consumed by the **existing** shared worker. Preserve source version, episode/SHOT ID, job ID/idempotency key, immutable input fingerprint, Director approval, stop/cancel, retry limit, render timeout and audit status. Default **one active expensive render** at a time until safe measurements justify a documented change. Use batch preparation for efficiency; do not start isolated infrastructures per SHOT.
4. **No blanket exception.** A genuinely new persistent architectural capability (not a SHOT implementation workaround) requires **separate, explicit Director authorization** describing why the existing services cannot handle it, predicted monthly CPU/RAM/storage/network cost, resource caps, time-to-live or retirement condition, rollback, and a verified cleanup plan. Without this written approval: STOP. Never create a temporary Railway service as a convenient testing shortcut.
5. Tests and diagnostics should use existing backend/unit-test infrastructure, the shared worker's bounded `DIAGNOSTIC` job mode or local ephemeral build steps as appropriate. An existing service must not be silently repurposed into a constantly running QA daemon; diagnostics must have bounded execution and no extra persistent instance.

## P0.2 — PostgreSQL for structured metadata, NOT a media warehouse

1. PostgreSQL is the **transactional source of truth for small structured state only**: episode/SHOT IDs, scripts, selected voice and cue timings, source Git SHAs, visual contracts, status, hashes, object keys, Director feedback/approvals, lineage, reference maps, audit and billing metadata.
2. **PROHIBITED for every new production path:** writing MP4/MOV, frames, screenshots, audio, ZIP, raw uncompressed JSON media payload or other large binary data into PostgreSQL `bytea`, TOAST or base64 fields, including `remotion_render.video_data`, `studio_clip`, `voice_clip_workflow` and any new byte storage. No database-backed temporary render cache. Do not introduce a parallel blob table disguised as a metadata record.
3. **Grandfathered, immutable exception:** existing Director-selected completed EP001 / EP002 / EP003 whole-film MP4 payloads (three pinned render IDs and SHA-256 values documented in `MEDIAOS_POSTGRES_DISK_RECLAIM_COMPLETE_20261117.md`) remain readable and untouched. **Do not delete or move them automatically.** This exception does NOT authorize writing future completed films to `video_data`.
4. New media must be written **outside PostgreSQL** to the existing approved object-storage layer after the **actual** code/permissions and reader contract are implemented and QA-verified. Use streamed upload/download, deterministic versioned object keys and content SHA-256; keep only metadata/object URI/hash/status/expiry in PostgreSQL. No external paid storage expansion or bucket creation without Director approval.
5. **FAIL CLOSED before new EP004+ MP4 write** if MediaOS still supports only legacy `video_data` insertion: do not run a production render that would silently fill PostgreSQL. The object-store write + protected MediaOS playback and signed URL/auth contract must be implemented, tested and promoted before first new media binary is saved. Source/voice and visual planning can continue in metadata-only mode while this is pending.
6. Large pre-existing media fields in legacy schemas may remain for backwards compatibility, but all **new writers** must be blocked and all **new readers** must prefer verified object storage, with an explicit fallback only for the three existing grandfathered masters. Do not silently migrate them or pretend the object-store pipeline is deployed today.

## P0.3 — Retention must be automatic and safe, without periodic manual cleanup

1. Every media artifact has a mandatory `artifactType`, `episodeId`, `shotId` when applicable, `sourceSha`, `objectKey`, `sha256`, `bytes`, `createdAt`, `retentionClass`, `expiresAt` (for temporary media), `approvalId` where applicable and an audit trail. A generated byte payload without a storage owner, retention class or lifecycle is rejected.
2. **Temporary** render fragments, scratch media, QA samples, failed uploads, rejected/non-Director-approved previews and intermediate assemblies live in object storage or bounded ephemeral job scratch with **explicit, configurable TTL and byte limits**. On success/failure/cancel: remove job scratch using `finally`-style cleanup and audit the deletion. A background retention task uses the **existing backend or render worker**, not a new service.
3. **Never auto-delete locked or still-needed source artifacts.** A fully completed and checksum-verified Director-approved final film is protected by default; keep any still-required selected original voice/provenance per Director rules. Transient intermediates are eligible for deletion only **after** a retained source lineage and any needed replacement preview/master have been verified. Pending Director review is protected until an explicit decision or separately approved expiration workflow.
4. Default policy proposal requiring implementation: temporary QA/scratch <=24h, superseded preview <=72h **after acceptance of its replacement**, and unapproved review versions retained until Director decision (with age alerts, not blind deletion). These are **target policy values, not already active TTL mechanisms**. Never treat 24/72h as permission to delete protected originals.
5. The system must keep **only current needed playable media**. For future episodes, retain the Director-approved full master and any separately authorized review/Short export; avoid indefinitely retaining old full-film WIP MP4s, every SHOT MP4 and standalone voice binaries. Preserve scripts, source files, final hash/provenance and human approvals.
6. Deduplicate immutable artifacts by content hash where safe, prefer stream-copy for unchanged shots and incremental renders. No unbounded `bytea`, raw video blobs, base64 logs, unlimited retry output or infinitely growing temporary storage.

## P0.4 — Strict resource cost, capacity, and admission gates

1. **No unauthorised charges:** all paid ElevenLabs/OpenAI/provider calls and material Remotion CPU renders require the existing explicit Director production/cost authorization; planning and saving do not spend. Record estimated and actual CPU time, memory, job duration, generated bytes, retries and provider usage per episode/SHOT/job; enforce limits. Never silently expand Railway storage, service count, RAM, CPU, AI credits or provider budgets.
2. Resource caps must be configured and enforced for every job. Fail closed if job estimates exceed approved budgets, if required artifact storage is not available or if the database is already near capacity. Do not create one-off Railway services to work around a failed cap.
3. **Primary PostgreSQL disk thresholds, relative to current provisioned capacity:** at **50% used** send a visible warning and identify rapidly growing relations, TOAST, WAL and retention candidates; at **65% used** block new media-producing operations until the capacity issue and true storage destination have been verified (metadata-only work may continue); at **75% used** enter incident protection mode: stop all nonessential disk-intensive work, do NOT attempt a blind `VACUUM FULL`, disk expansion or deletion. These thresholds are **Director policy requirements; automated metering/admission logic is NOT YET IMPLEMENTED**.
4. Budget protections must check **both** `pg_database_size`/relation/TOAST and actual Railway volume used/capacity plus running memory/CPU usage. A small count of live binary rows does not imply the physical volume has shrunk. Normal `VACUUM` is routine; `VACUUM FULL`, `CLUSTER`, `REINDEX` and major data migration require a verified independent backup, available headroom, a maintenance window, explicit Director approval and before/after hash QA. Never manually delete WAL.
5. Monitor daily used/free disk and projected days to thresholds, monthly invoice run rate, shared worker CPU/RAM spikes, failed/cancelled jobs and orphan object bytes. **Alert early; never silently pay/expand resources**. If the available connector cannot configure a real alert/monitor, record that as an **unimplemented requirement** and provide a manual or existing-service fallback; do not claim monitoring has been installed.

## P0.5 — Mandatory pre-production and post-production checks

Before executing any new episode/SHOT:
- Read `AGENTS.md`, `PROJECT_STATE.md`, this policy, the Director roadmap and relevant episode's locked sources.
- Verify production Railway baseline is **three** services; no pending/staged infrastructure change; the existing worker can handle the job; memory/disk forecast and explicit monetary budget/approval.
- Verify selected source audio and locked shots are not modified; job storage path is **object storage, not `video_data`**; retention metadata, max size and time, sha256, idempotency, rollback and cleanup exist.
- If any gate fails, **STOP and report the blocker, instead of inventing a new server/volume/bucket or writing a large blob into the database**.

After every production job or wave:
- Check measured disk and RAM usage, object-storage bytes, status and cost; verify no new unexpected Railway services or volumes; ensure scratch/aborted/rejected artifacts were cleaned under approved retention.
- Verify protected final-master hashes, actual playback for newly approved master, and working source lineages.
- Record evidence, real provider IDs and measured before/after values in `PROJECT_STATE.md` on the actual working Git branch and the relevant engineering handoff. Treat a source-only PR as **NOT IMPLEMENTED** until live verification.

## P0.6 — Implementation backlog / acceptance (NOT DONE by documenting)

These changes require separate implementation and tests before an automatic guarantee exists:
1. **Hard service-count guard:** tests + preflight reject new SHOT/QA/canary Railway service creation. CI/static checks should inspect source/config for infrastructure creation paths; runtime inventory check must compare expected three service names before every deployment.
2. **Object-store binary writer and reader:** stream MP4/voice/preview to existing recovery/approved media bucket (respect separate recovery namespace and permissions); commit metadata only; authenticated playback; SHA check; non-public URLs; three legacy master DB fallback.
3. **Database binary admission protection:** integration tests reject new `remotion_render.video_data` and other bytea media writes while preserving legacy read access; database media tables show no new large binary payload post-render.
4. **Artifact lifecycle worker in existing services:** bounded TTL/byte quotas and protected Director-lock/pending-review rules, idempotent retention deletion with audit; tests cover failed jobs and orphan uploads.
5. **Production storage/cost monitoring and guard:** thresholds 50/65/75%, real Railway disk usage and DB bloat detection, max render concurrency 1, CPU/RAM/cost ceilings, no new paid cloud resources automatically, alerts and rollback.
6. **End-to-end acceptance test:** one new explicitly approved SHOT generated by existing shared worker, with **zero new Railway services**, **zero new PostgreSQL MP4/audio bytes**, bounded external media storage, full movie playback + SHA matching, protected old 3 masters, stable disk footprint and retention/cleanup verified.

**Non-negotiable acceptance:** a new episode must not require another bulk Railway service purge or PostgreSQL `VACUUM FULL` to keep running. These rules have no expiration; supersede older example workflows that created a Railway one-shot service for each SHOT or saved all previews directly in PostgreSQL. Never misrepresent documentation as deployed enforcement.
